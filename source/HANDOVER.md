## 二、最重要的一个概念：三种运行模式

整个站的行为由 `config.js` 里两个值决定。**没搞清这个，你会以为很多功能坏了。**

| `proxyUrl` | `demo` | 模式 | 表现 |
|---|---|---|---|
| `""` | `false` | 静态回退 | 用 HTML 里写死的内容，完全不请求后端 |
| 任意 | `true` | **演示模式（← 当前就是这个）** | 用 `app.js` 内置示例数据渲染，写操作只弹「模拟成功」，不真存 |
| 已填 | `false` | 数据驱动 | 真正读写飞书多维表格 |

### ⚠️ 最容易踩的坑

`app.js` 里的判断是 **`demo` 优先于 `proxyUrl`**：

```js
function api(path, opts) {
  if (DEMO) return demoApi(path, opts);   // ← demo:true 直接短路，proxyUrl 根本不会被用到
  ...
}
```

**所以后端部署好、`proxyUrl` 填上之后，必须同时把 `demo` 改回 `false`**，否则页面看起来一切正常，但你看到的全是假数据，一条真记录都没读。这个坑不会报错，只会让你困惑很久。

## 五、已知限制和风险

这些不是 bug，是 MVP 阶段的取舍。但**上线前你需要知道**。

### 🔴 `/api/request` 是公开的、无鉴权的写接口

`cloud-function/index.js:299` —— 「申请拍摄」表单的提交接口**不需要登录**，任何人只要知道云函数地址，就能直接往你们的飞书「活动记录」表里插数据。

**并且没有任何限流、没有验证码。** 这是给外部社团提交申请用的，设计上就得开放，但意味着**被人写脚本刷几千条垃圾记录是完全可行的**。

上线前建议至少加一层：腾讯云 API 网关的限流插件，或者简单的 IP 频率限制。

### 🟠 登录 token 是静态的，永不过期

`cloud-function/index.js:263-274` —— 口令验证通过后，云函数返回的是环境变量 `MEMBER_TOKEN` 的**原值**，一个固定字符串。它不是签名 token，没有有效期，也没有和用户绑定。

含义：
- 任何人拿到这个 token，就**永久**拥有写权限
- 想吊销，只能去改环境变量 `MEMBER_TOKEN`，然后**所有社员都得重新登录**
- token 存在浏览器的 `sessionStorage` 里

`PLAN.md` 里写明了这是 MVP 的有意选择（「MVP 登录用统一访问口令」）。社团内部用问题不大，但别把它当成真正的账号系统。

### 🟠 成员表存的是个人信息，而登录机制只有一道口令

新增的「成员」表里有**姓名、班级、学号**。这比活动照片敏感得多。

云函数对这张表做了比其他表更严的处理：**读和写都要求登录**（其他三张表游客可读）。页面上的名册也**不显示学号**。

但底下垫着的仍然是上面那个「统一口令 + 永不过期 token」。口令一旦在群里传开、或者某个人的浏览器被别人用了，全社的学号就都能被读走。**上线前请把这一节前两条（限流、token）处理掉。**

### 🟠 读取只取前 100 条，没有分页

`cloud-function/index.js:133-139` 的 `listRecords()` 写死了 `page_size=100`，而且没有翻页循环。代码里自己有注释承认这一点。

**活动或照片记录超过 100 条之后，页面就显示不全了，而且不会有任何报错提示。** 按现在的数据量（示例是 6 个活动）短期够用，但这是个会静默出问题的定时炸弹。

### 🟡 其他

- **CORS 默认 `*`**（`index.js:39`）。生产环境应该把 `ALLOWED_ORIGIN` 收紧成你们的站点域名。
- **单文件上传约 ≤ 4–5MB**。受腾讯 API 网关 body 上限 + base64 编码放大约 33% 的双重限制。大文件和视频请走百度网盘链接那条路。
- **飞书列名必须一字不差。** 见下一节。

## 六、改代码前必读的三条约定

### 1. 字段名在三个地方重复，改一处必须同步三处

飞书多维表格的中文列名（`活动名称`、`照片数`、`网盘链接` …）硬编码在：

- `app.js` 顶部的 `F` 常量
- `cloud-function/index.js` 里的 `F` 常量
- `SETUP.md` 的建表说明表格

**任何一处对不上，读写就静默失败**（拿到 `undefined`，不报错）。`integration.test.js` 就是专门守这个的 —— 它会检查这三处是否一致。改字段名之后一定要跑它。

### 2. `styles.css` 是「底层 + 覆盖层」结构，改风格改覆盖层

> 2026-10-08 更新：下面这段原来的描述已过时，以本段为准（详见第二十四节）。

- **前半部分**：原始底层样式（已删掉被后面完全覆盖的声明和页面里不存在的选择器）
- **「Apple 结构 + Sequoia 配色」大标题之后**：覆盖层，分成表单、材质分级、尺度系统、squircle、动效、导航、Liquid Glass 等小节
- **设计令牌只在文件开头唯一的 `:root` 里**（颜色 / 字体 / 圆角 / 控件尺度）

同一个选择器仍可能出现两次（底层一次、覆盖层一次），后面那条生效 —— 剩下的都是「部分覆盖」，删任何一条都会改变渲染。**无障碍覆盖（`prefers-reduced-transparency` 等）必须留在文件最末尾**，见第二十三节。

改样式请改覆盖层对应的小节，不要再往文件末尾叠新层。

### 3. 改配色或 CSS 必须跑 `design.test.js`

它会验证正文色、次要文字色、强调色在底色上的 WCAG 对比度是否达标，顺便检查 CSS 大括号是否配平。

**注意 `--text-muted` (#667085) 的对比度是 4.56:1，标准线是 4.5:1 —— 只富余 0.06。** 把这个灰色再调淡一点点，测试立刻就红。

## 七、我在交接前改了什么

2026-08-30 改了三处，都是版式问题，逻辑一行没动。原因是整页留白严重过量：实测**全页 36% 的高度是 section 的 padding**。

1. **收紧全站垂直节奏**（追加在 `styles.css` 末尾）
   `section` 的 padding 上限从 118px 降到 88px。改前在 1440px 宽下相邻区块之间隔着 236px 纯空白。

2. **空态区块的 padding 单独减半**（用 `:has(.empty-state)`）
   「照片合集」区原本内容只有 74px 高，却撑成 330px —— **78% 是空白**。「活动素材库」同理（138px 内容撑成 432px）。这两块之所以是空的，就是第三节 ① 说的那个问题。

3. **修正一处文不对题的标签**（`index.html:159`）
   `<legend>活动类型</legend>` 底下装的其实是 **CAS 时长录入**（C / A / S 三个小时数输入框，`app.js:505` 把它们拼进「描述」字段）。页面上显示成 `C [0]` `A [0]` `S [0]`，既没有单位也没有说明。已改为「CAS 时长（小时，可留空）」。

**效果**：整页高度 7629px → 6759px（−11%），首屏从只能看到 hero 变成能看到 hero + 统计 + 下一个区块的标题。四套测试改动后仍然全绿。

> `:has()` 选择器需要 Chrome 105+ / Safari 15.4+ / Firefox 121+。老浏览器上只是空态区块留白照旧，不会出错。

## 十一、成员信息采集与 AI 自动分组

这是 2026-08-30 新提的需求，分两半：**信息采集**（已做完）和 **AI 自动分组**（没做）。

### 已完成：信息与技能采集

页面上新增了「成员资料与技能」区块（导航栏「成员」，锚点 `#members`）。

**基础信息**：姓名、班级、学号、性别、社内职位、补充说明。性别是单选，选项为 `男 / 女 / 无性别`，另外还留了「不填」——**不填和「无性别」是两件事**，前者是不想说，后者是明确的身份表达，别把它们合并。

**技能标签**：两种操作方式，都能用。

- **拖拽**：把标签从「可选技能」拖进「我掌握的技能」，拖回去就是移除。
- **点选**：点一下即可加入/移出。键盘 Tab + 回车同样有效。

> **为什么不用 HTML5 的 `dragstart`/`drop`：那套 API 在手机浏览器上根本不触发。**
> 这里用的是 Pointer Events，鼠标和触屏共用一套代码。已经在 1440px 桌面和 390px 触屏两种环境下实测过拖拽和点选。
>
> 相关的两个坑，改这块代码时留意：
> 1. 标签的 CSS 必须保留 `touch-action: none`，否则手机上一拖变成滚动页面。
> 2. 拖拽结束后要吃掉紧跟的那次 click，但**不能用布尔开关**——鼠标拖完会补一个 click 把开关清掉，触屏拖完不会，开关就卡住了，之后每次拖拽都会吞掉用户的下一次点击。现在用的是时间戳（400ms 窗口），会自愈。

**技能词条**改 `app.js` 里的 `SKILL_POOL` 常量即可，界面自动跟着变。当前 12 个：拍照、修图、拍视频、剪视频、调色、灯光、收音、无人机、平面设计、文案、排版、活动统筹。

**数据落地**：飞书新建第 4 张表 `成员`，建表字段见 `SETUP.md` 表 4，云函数环境变量多一个 `TABLE_MEMBERS`。

**两个接口，都要求登录**：

| 接口 | 行为 |
|---|---|
| `GET /api/members` | 读名册。**未登录返回 401** —— 和其他三张表不同，因为含学号 |
| `POST /api/members` | 保存资料。**按学号 upsert**：同一个学号重复提交是覆盖更新，不会产生重复记录 |

页面上的名册**只显示姓名、班级、性别、职位、技能，不显示学号**。这是有意的，别为了「方便核对」把它加回去。

**现在就能试**：演示模式下有 3 条示例成员数据，拖拽、点选、名册渲染都能看到效果，不需要部署后端。

### 接口已预留：AI 自动分组

**除了「真正调模型」那一个函数，其余全部实现好了。** 接手的同学拿到 API Key 之后，填一个函数就能跑通。

#### 只差这一处

`cloud-function/index.js` 里的 **`callModel(prompt)`**。它现在直接抛错：

- 没配 `LLM_API_URL` / `LLM_API_KEY` / `LLM_MODEL` → 抛 `LLM_NOT_CONFIGURED`
- 配了但函数没实现 → 抛 `LLM_NOT_IMPLEMENTED`

两种情况接口都返回 **501**，前端会显示「接口已就绪，但还没接大模型」——不会让人误以为是坏了。

函数上方的注释里写好了 DeepSeek 和 Claude 两家的请求格式（URL、headers、body、从哪取值），照着填即可。入参是拼好的 Prompt 字符串，返回模型输出的纯文本。

#### 已经实现的部分

| 环节 | 状态 |
|---|---|
| `POST /api/group` 路由 + 登录校验 | ✅ |

**学号不会发给模型。** `membersForPrompt()` 只取姓名、职位、技能三样，分组用不到学号。

#### 结果不会被当成一定对

`checkGroups()` 会挑出这些问题，原样显示在结果上方的警告条里：

- 有人没被分到组 / 有人被分进多个组
- 组数和要求不符
- 各组人数相差超过 1 人
- **出现了名册上没有的人**（模型编造人名，这个必须抓）
- 某组没有任何已登记的技能

这些是**警告不是拦截**——结果照常返回，但明确告诉人哪里不对，由人决定要不要重跑。

这一套在 `cloud-function/test.js` 里有测试，**不需要真模型就能验证**（`_parseGroupJson` / `_checkGroups` 已导出）。

#### 分组结果会留档到飞书

结果写进第 5 张表「分组」，**每组一行**，同一次分组的几行用相同的「批次」（时间戳）串起来。建表说明见 `SETUP.md` 表 5，环境变量 `TABLE_GROUPS`。

留档的意义是**结果能在飞书里人工调整** —— AI 出初稿，人拍板。

**留档是附加动作，不会拖垮主流程**：没配 `TABLE_GROUPS` 就跳过（分组照常可用，只是不落库）；写入失败也只在结果里多一条警告，不会让「算出来了」这件事跟着一起失败。

#### 动手前仍然要想清楚的两件事

**1. 费用不是问题，支付方式才是**

| 模型 | 单次成本 |
|---|---|
| Claude Sonnet 5（$2 / $10 每百万 token） | ≈ 0.3 元 |
| Claude Opus 5（$5 / $25 每百万 token） | ≈ 0.7 元 |

> DeepSeek 的具体单价我没有权威来源，没敢往上写，你们自己去官网确认。上面 Claude 的价格是查证过的。

原来是「DeepSeek Harness 风」——品牌蓝 `#4D6BFE`、白卡片、16px 大圆角、投影、毛玻璃。现在改成参考 Loro Piana / Louis Vuitton 的克制路线。

### 具体改了什么

| | 改前 | 改后 |
|---|---|---|
| 底色 | 冷灰 `#f4f5f7` | 暖本白 `#f4f2ed` |

| 圆角 | 56 处声明 | **全站 0** |
| 阴影 | 49 处声明 | **全站 0** |

| 分区 | 靠色块和卡片 | 靠发丝线和留白 |

实测确认：全页 459 个元素，圆角、阴影、毛玻璃、彩色背景**全部为 0**。

### 改这块要知道的三件事

**1. 整层追加在 `styles.css` 末尾，删掉就退回原样。**

标着「扁平化 / Quiet luxury 覆盖层」的那一段（第 10、11 小节也属于它）。这是本项目一贯的分层做法——不动前面 2300 行，只在末尾覆盖。

**2. 那个通配符 `!important` 是有意的。**

```css
*, *::before, *::after {
  border-radius: 0 !important;
  box-shadow: none !important;
  backdrop-filter: none !important;
}
```

圆角/阴影/毛玻璃在前文散布 130 多处，逐条改既啰嗦又容易漏。通配符优先级最低（0），不用 `!important` 压不住任何具体选择器。**这是整层唯一用 `!important` 的地方**，下面那些有意的重新设计都是靠正常优先级。

**3. 字体权重之前是错的。**

CSS 里用了 26 处 `font-weight: 800/900`，但 Google Fonts 只加载了 400/500/600 —— 一直在用浏览器合成的假粗体。现在改成加载 300/400/500，字重也收到了 300–500 区间。

### 还没做的视觉功课

这套风格的核心是**大图**，而这个站现在几乎没有照片（`assets/` 里 63 张图没被引用，见第三节 ②）。

**排版已经准备好承接大图了，但图还没接进去。** 接上之后效果会和现在差一个量级——现在只是「干净」，接了图才是「像那么回事」。这是下一步性价比最高的一件事。

## 十三、改成 Sequoia Capital 风格（深色 + 绿）

参考 [sequoiacap.com](https://sequoiacap.com/)，用户提供了他们的完整前端 HTML，所以这次的数值是**照抄的，不是猜的**。

### 照抄了什么

| 项 | 取自他们的值 |
|---|---|
| 头部高度 | 96px（平板/手机 80px） |
| 页面边距 | 48px（手机 24px） |
| hero 高度 | 500px @≥1920 / **380px @1024–1919** / 220px @<768 |
| 卡片网格 | `aspect-ratio: 1` 的**正方形**，`repeat(4,1fr)` → 3 → 2 → 1 |
| 卡片发丝框 | `inset: 16px` 的 1px 内嵌边框（他们整站的骨架） |
| 图片遮罩 | `linear-gradient(180deg, transparent 50%, rgba(0,0,0,.5) 100%)` |
| 线色 | `#aeada9`（浅色版）；深色版换成 `#3a3733` |
| 绿 | `#007354` 实心块 / `#00a071` 强调 |

### 重心（用户特别要求）

Sequoia 的做法是：**hero 短，不占满屏**——1440px 宽下只有 380px 高，约占视口 42%，所以第一屏就能看见下面图块的顶边。视觉重量压在中下部的方形图片网格上，而不是顶部大标题。

所以 hero 被改成只有一行居中衬线标题，原来的两个按钮和统计数字都移了出去（统计变成 hero 下方一条发丝线行）。

### 三处有意偏离

**1. 字体换了。** 他们用的 Rosart / Unica77 / Pitch Sans 都是商业授权字体，托管在自家 CDN：

| 他们的 | 我用的 |
|---|---|
| Rosart（巴洛克衬线） | EB Garamond + Noto Serif SC |
| Unica77（Lineto 无衬线） | Inter + Noto Sans SC |
| Pitch Sans（Klim） | **Fragment Mono** —— 他们页面里也加载了这个 Google 字体 |

**2. 正文灰调深了。** 他们的 `#8d8c89` 在自家底色上只有 **3.15:1**，达不到 WCAG AA。浅色版我用了 `#6f6d68`（4.84:1）。网格线仍用他们的原值 `#aeada9`（纯装饰，不承载文字）。

**3. 绿色的选择受对比度约束。** `#007354` 对纯白只有 **2.99:1**，差 0.01 过不了 `design.test.js` 的门槛，所以它只能做实心块底色（其上白字 5.87:1，很好），不能当 `--accent` 令牌。`#00a071` 是唯一同时满足「深底 ≥3」和「白底 ≥3」的绿，所以强调色用它。

### 时间线接上了封面图

Sequoia 式的方形图块**靠图片撑起来**，没有图就是一排空方框。所以活动卡片接上了封面：

- 走已有的飞书「封面」附件字段，**演示和连接两种模式同一条代码路径**（没有特判）
- 演示模式的 6 张封面复用了 `assets/events/` 里按名字一一对应的照片
- 顺带让第三节 ① 提到的 `DEMO_IMAGES` 死代码重新有了用途

> 注意：这和第三节 ① 说的「照片墙示例被有意删除」是**两回事**。`DEMO_DATA.photos` 我一行没动，那条测试断言仍然锁着。

### 排查过程中修掉的两个隐藏 bug

**1. 一条冷灰带。** hero 和统计行之间有一条 `#f7f8fa` 的冷灰带。计算样式查下来所有元素都报正确的底色，是**像素采样**才证明确实不一样。根因是 `body::before` 有个 `position: fixed` 的冷灰渐变铺在最底层（z-index -2），凡是没有不透明 section 盖住的缝隙就露出来。深色化后这个渐变已改成纯色。

**2. 旧规则劫持了新结构。** `.timeline-list article > *` 把子元素强制 `position: relative`，让绝对定位的封面图退化成一条窄带；`.timeline-list article > span` 又给所有 span 套了 `rgba(255,255,255,.38)` 白底——`.tile-scrim` 是 span，于是整块盖了层白纱。都在新层里逐个还原了。

### 层数已经偏多

`styles.css` 现在叠了 6 层覆盖（原始玻璃拟态 → DeepSeek → 扁平化 → 层次 → Sequoia → 深色绿）。**每加一层就要花力气对付上一层的残留**，上面那两个 bug 就是这么来的。

下一次再大改风格，建议不要再叠第 7 层，而是把前面几层压平重写一遍。现在还能维持，是因为配色令牌已经归一到文件开头唯一的 `:root`（`design.test.js` 校验的就是那一处，改配色只改那里）。

### 合并过程中引入并修掉的四个 bug

全都是我自己在这一轮造成的，记下来是因为它们都属于**同一类**（选择器优先级 / 副作用）：

1. **「上传/贴链接」按钮在未登录时照样显示** —— 给按钮写 `display: inline-flex` 会盖掉浏览器默认的 `[hidden] { display: none }`。修法：显式加 `[hidden] { display: none !important }`。

## 十五、表单控件统一 + 材质分级

### 表单：此前并存三套

实测下来是这样（这不是主观判断，是量出来的）：

| 分组 | 圆角 | 底色 | 高度 | 内边距 |
|---|---|---|---|---|
| 申请表单 / 招新 / 弹窗 | 10px | `#f5f5f7` | 53 | 13/14 |
| 成员表单 / 组数 | **12px** | **#fff** | 51 | 12/14 |
| CAS 数字框 | 10px | `#f5f5f7` | **45** | **9/10** |
| 上传模式单选 | **0，无边框** | — | — | 0 |

**根因**：底层 `.request-form input`、`.cas-grid input` 这类 `(0,1,1)` 选择器压过了通用的 `input`。所以统一规则里把同一批选择器**全列了一遍**，靠「同优先级、更靠后」取胜。

### 现在的规格（一套）

白底 + `1px #d2d2d7` + `12px` 圆角 + `48px` 最小高 + `17px` 字 + `13px 16px` 内边距。

白底带边框在白区和灰卡上都成立，**所以不依赖容器底色**——这是能全站统一的关键。

顺带做的细化：

- **下拉框**换成自绘箭头（原生箭头各平台长得不一样）
- **文件选择**的默认按钮换成绿色小胶囊
- **CAS 三个数字框**：C/A/S 变成字段内部前缀（`padding-left: 38px`），高度与其他字段一致
- **入库方式**单选改成 Apple 的分段控件（用 `:has(input:checked)` 上色，原生 radio 视觉隐藏但仍可聚焦）
- **焦点态**：绿色边框 + `outline: 3px rgba(0,115,84,.16)`

> 焦点环用 `outline` 而不是 `box-shadow`，因为上面的扁平化重置把阴影全禁了。

**验证方式**：跑一遍所有 `input/select/textarea` 的计算样式，聚合成「样式指纹」。结果 4 组，差异全是功能性的——CAS 前缀留 38px、文本域 120px 高、下拉留 42px 放箭头；圆角/底色/边框/字号/高度完全一致。

### 材质分级（Apple Design skill）

参考 `emilkowalski/skills` 的 `apple-design/SKILL.md`。三条规矩：

1. 浮动区域用 `backdrop-filter` 做半透明，**但不叠第二层**
2. 面越大，模糊和阴影越重；压在杂乱内容上的再重一点
3. 需要聚焦时用遮罩压低背景；不该打断流程时只用偏移 + 透明度

实现分三层：

| 层 | 元素 | 材质 |
|---|---|---|
| **A 浮动 chrome** | `.site-header` | `rgba(255,255,255,.72)` + `blur(20px) saturate(180%)`，内容从下面穿过 |
| | `#back-to-top`、`.demo-badge` | 小浮动控件，`blur(10px)`，模糊比大表面轻 |
| **B 大表面** | `.modal` 遮罩 | `rgba(0,0,0,.42)` + `blur(6px)`，把背景推远制造聚焦 |
| | `.modal-card` | **实心白** + `0 32px 80px` 深阴影 |
| **C 小控件** | 按钮 / 标签 / 卡片 | `0 1px 2px` 级别的轻阴影 |
| | `.tile.has-cover` | `0 6px 20px`——压在照片上，按「杂乱内容要更重」加深 |
| **不打断流程** | `.toast` | 半透明 + 模糊 + 偏移，**不加遮罩** |

其他照 skill 做的：

- **颜色放实心层**：弹窗卡片是实心白，不是半透明——半透明前景上的文字会发灰
- **半透明面上的文字**：导航文字提对比 + 字重 500 + 微开字距，不用平灰
- **边缘用渐变不用硬边框**：导航条底边是 `::after` 渐变，不是 1px 实线
- **入场「材质化」**：弹窗 `@keyframes materialize` 让模糊与缩放一起动，不是单纯淡入（并尊重 `prefers-reduced-motion`）
- **输入框保持平面**：它们在卡片里，再加阴影就是第二层材质了

### 一个结构性说明

底层有 49 处 `box-shadow`、28 处 `backdrop-filter`（旧玻璃拟态留下的带色渐变和厚阴影）。做法是**先一次性清零，再按层级显式加回来**——清零那条和材质那节都用 `!important`，同优先级下靠后者胜。

这样的好处是：**全站的材质只有一个地方定义**，想知道某个元素为什么有阴影，只看「材质分级」那一节即可。

**自动验证**：写了个检查脚本，遍历所有元素找「祖先里还有半透明层」的情况，确认没有相叠。改材质时值得重跑一遍。

## 十六、圆角的尺度系统与连续曲率

### 先量后改：问题是什么

实测全站「圆角 ÷ 高度」的比值：

| 元素 | 高 | 圆角 | 比值 |
|---|---|---|---|
| 输入框 | 50 | 12 | 0.240 |
| 名册卡 | 119 | 14 | 0.118 |
| 记录卡 | 274 | 18 | 0.066 |
| 表单面板 | 912 | 18 | **0.020** |

**圆角几乎恒定在 12–18px，而尺寸跨了 50→912px。** 912px 高的面板配 18px 圆角，观感就是「方盒子上啃了一小口」。这不是审美问题，是比例失配。

### 改法一：圆角随尺寸递增

建了一套阶梯 `--r-1` 到 `--r-6`（8 / 10 / 12 / 16 / 22 / 28），按元素尺寸分配。改完后是单调的：

```
高 40  → 胶囊       高 44  → 12
高 119 → 16         高 274 → 22
高 458 → 28         高 894 → 28
```

另有**同心圆角**：紧贴嵌套时 `内圆角 = 外圆角 − 间距`，这样父子的弧线平行。分段控件就是这么算的——外框 12、内边距 3、所以内圆角 9。间距很大时不适用（子元素视觉上已经独立）。

### 改法二：连续曲率（squircle）—— 苹果圆角的真正做法

**这是关键。** 普通 `border-radius` 是四分之一**圆弧**，弧线与直边相接处曲率是突变的；半径越大，那个「折点」越明显。苹果用的是**超椭圆**（continuous corner），曲率平滑过渡进直边——SwiftUI 里就是 `RoundedRectangle(style: .continuous)`。

CSS 现在有对应属性 `corner-shape`：

| 用在哪 | 值 | 理由 |
|---|---|---|
| 卡片 / 面板 / 图块 / 弹窗 | `squircle` | 半径越大收益越明显 |
| 输入框 / 列表行 / 分段控件 | `superellipse(3)` | 更缓的指数，效果克制 |
| 按钮 / 标签等胶囊 | `round` | 胶囊两端本来就该是半圆，套 squircle 反而不对 |

> **兼容性**：`corner-shape` 目前只有 Chrome 139+ 支持，Safari / Firefox 还没有。整段包在 `@supports (corner-shape: squircle)` 里，不支持的浏览器回落成普通圆弧，**版式完全不变，只是角的曲率不同**。
>
> 社员多数用手机，iOS 上是 Safari，**大概率看到的是回落版本**。所以两种情况都得好看——这也是为什么圆角尺寸本身要先修对，squircle 只是锦上添花。

### 改法三：输入框去掉细边框

原来是「白底 + 1px 描边」，在 44px 的控件上那条细边显得琐碎。改成**填充式无边框**：

- 静态：`rgba(0,0,0,.045)` 填充，无边框
- 悬停：填充加深到 `.07`
- 聚焦：**填充转白 + 2px 绿环** —— 状态变化靠明暗对比，比改边框颜色明显得多

填充式字段要在白底上才读得出来，所以表单容器一并改成白卡。技能标签也去掉了描边，跟输入框同一套填充语言。

**验证**：跑一遍所有控件的描边，确认 `input / select / textarea / skill-chip / card / tile` 全部为 `0px`，且填充只有一种值。

### 控件尺度

统一为 **高 44 / 字 17 / 左右内边距 16**（`--ctl-h` / `--ctl-fs` / `--ctl-pad-x`）。44 是「刚好一行字 + 上下呼吸」的比例，比原来的 48 紧凑。文本域升一档圆角（16）因为它更高。

### 没拿到的东西

Apple HIG 的圆角官方数值**没抓到**——那些页面是 JS 渲染的，抓下来只有标题。`emilkowalski/skills` 的 `apple-design` 也**明确不涵盖圆角和表单控件**（它讲材质、动效、字体尺度）。

所以上面的阶梯是按「同心 + 次线性递增」这两条通用原则推出来的，**不是照抄苹果的数值**。`corner-shape` 那部分倒是有据可依——你给的 Sequoia HTML 里就有 `@supports (corner-shape: superellipse(2))`，说明这属性已经在真实站点上用了。

## 十七、动效规范 + 圆角加圆

### 圆角加圆

连续曲率的角在**同一数值下比圆弧「读起来更紧」**，所以阶梯整体上调约 1.3×：

| | 旧 | 新 |
|---|---|---|
| `--r-1` 角标 | 8 | **10** |
| `--r-2` 小控件 | 10 | **13** |
| `--r-3` 输入框 | 12 | **16** |
| `--r-4` 列表行/文本域 | 16 | **22** |
| `--r-5` 卡片 | 22 | **30** |
| `--r-6` 大面板/图块/弹窗 | 28 | **40** |

分段控件的同心关系跟着更新：外框 16 − 内边距 3 = 内圆角 **13**。

### 动效：按 apple-design skill 修的三处

skill 里关于动效的内容很具体，而且**直接点出了我现有拖拽实现的两个缺陷**。

**1. 缺 `setPointerCapture`（真 bug）**

> "Employ `setPointerCapture` so tracking persists beyond element bounds."

原实现只在 `document` 上听 `pointermove`。指针快速移出标签、或移出窗口再回来，跟踪就可能断。已在 `pointerdown` 时对标签调用 `setPointerCapture`，`pointerup` 时释放。

**验证**：拖到窗口四个角再放开，拖影始终跟随 ✅

**2. 没保留抓取点（手感问题）**

> "Respect grab offset: track where the user grabbed the element, not its center."

原来拖影是 `transform: translate(-50%,-50%)`，也就是**标签会瞬间跳到指针正中**——手感像被抢走。现在记住按下时指针在标签内的相对位置（`grabX/grabY`），整个拖动过程保持不变。

**验证**：在距标签左上角 (8,6) 处按下，拖动中拖影左上角与指针的偏移实测 (9,7) ✅（差 1px 是拖影 `scale(1.04)` 造成的视觉盒偏移）

**3. 位移阈值 6px → 10px**

skill 建议 ~10px 的迟滞，低于此仍算点击。

### 补上的动效

| 项 | 做法 | 依据 |
|---|---|---|
| **按压反馈** | `:active { transform: scale(0.97) }`，100ms ease-out | "Respond on pointer-down, not on release" —— `:active` 在按下瞬间就触发 |
| 大卡片按压 | `scale(0.994)`，比小控件轻 | 整块缩放太多会晃 |
| 拖影 | `scale(1.04)` | 读作「被拿起来」 |
| 只动 transform / opacity | 缓动 `cubic-bezier(0.32, 0.72, 0, 1)` | "Animate only transform and opacity"（合成器友好） |

### 无障碍偏好（skill 明确要求的三项）

```
prefers-reduced-motion    → 去掉位移与弹性，只留短促透明度过渡
prefers-reduced-transparency → 提高不透明度、去掉所有 backdrop-filter
prefers-contrast: more    → 实底 + 明确描边，正文色加深
```

### 没做的（诚实记录）

skill 里这些**我没实现**，因为当前交互用不上，硬加反而是过度设计：

- **弹簧参数**（damping 1.0 / response 0.3–0.4）—— 现在没有惯性动画，标签是离散落位，不是自由拖甩
- **速度接管与动量投影**（`project()` 公式）—— 同上，松手即落位，没有抛掷
- **橡皮筋边界**（`rubberband()`）—— 没有可越界拖动的区域
- **2D 拆成独立 X/Y 弹簧** —— 没有弹簧
- **弹窗出场动画 + `transform-origin` 锚定触发元素** —— 关闭是 `display:none` 直接移除，要做出场得改 JS 时序

如果以后给分组结果加「拖动调整成员」，上面前四条就都用得上了，`apple-design/SKILL.md` 里有现成的公式。

## 十八、导航条：居中浮岛 + Liquid Glass

### 起因：右上角登录按钮「重心不对」

先量再改。原状实测：

| 指标 | 实测 | 问题 |
|---|---|---|
| 按钮高 / 导航条高 | 36 / 52 = **69%** | 太满，上下各只剩 8px |
| 字号 / 胶囊高 | 12 / 36 = **0.33** | Apple 的胶囊控件通常 0.40–0.44，低了显得「充气发胖」 |
| 几何居中 | 中线 26.0 = 条中线 26.0 | 这项本来就是对的 |
| 文字墨迹 | 距顶 7.0 / 距底 8.0 | **偏高 0.5px** |

所以「重心不对」是两件事叠在一起：**质量太重** + **光学重心偏上**。

### 两步修

**第一步：把按钮调轻。** 高 36→30（占 58%），字重 500，比例回到 0.40。

**第二步：光学居中。** 中文字形的墨迹在行盒里偏上约 0.5px，flex 居中只把「内容盒」放正，看到的字仍偏高。补 `padding-top: 1px`（居中后净下移 0.5px），实测墨迹上下差从 1.00px 降到 **0.00px**。

> 这是「几何居中 ≠ 视觉居中」的典型例子。以后调中文按钮都要留意。

### 第三步：改成居中浮岛（更根本的解法）

按钮之所以显得重，根本原因是**通栏导航条太空**——1440px 宽的条里只有零星几个元素，右上角一颗实心胶囊就成了唯一的重量。

收成**居中浮岛**后，品牌 / 链接 / 登录被同一块材质包住，按钮不再是「空条里的一块重物」，而是材质的一部分。实测浮岛宽 493px、水平居中偏差 **0.0px**。

> 顺带一提：**Apple 官网导航右上角其实没有实心胶囊按钮**，只有搜索和购物袋图标。实心 CTA 放导航条是营销站的做法。但登录入口确实需要被看见，所以是做轻而不是去掉。

### Liquid Glass 的四个要素

Apple HIG 是 JS 渲染的，**官方数值抓不到**，所以下面是按这个材质的已知视觉特征实现的，不是照抄：

| 要素 | 实现 |
|---|---|
| 玻璃本体 | `backdrop-filter: blur(28px) saturate(190%) brightness(1.04)` + `rgba(255,255,255,.5)` |
| 镜面高光边 | `inset 0 1px 0 rgba(255,255,255,.95)`（顶亮）+ `inset 0 -1px 0 rgba(255,255,255,.32)`（底次亮） |
| 顶部薄光 | `::before` 渐变，从 50% 白衰减到 62% 处透明——光顺着弧面滑下去 |
| 浮起 | `0 10px 34px rgba(0,0,0,.11)` + `0 2px 6px rgba(0,0,0,.05)` |

配套：内容从浮岛下方穿过（不是不透明挡板）；导航文字字重 500（skill 要求「半透明面上不用平灰、略加字重」）；活动项用淡绿胶囊底。

**验证过的两条**：半透明层没有相叠 ✅；玻璃压在照片上时，红墙与人影能透出来但文字仍清晰。

### 一个测试脚本的坑

用 `page.screenshot({clip})` 截固定定位元素会翻车——`clip` 用的是**文档坐标**，页面滚动后固定元素不在裁剪区里，截出来是空白。**要截浮动 chrome，用矮视口 + 整屏截图，别用 clip。**

## 十九、字体换成 SF Pro（系统字体栈）

### 一个授权前提

**SF Pro 是苹果的专有字体，授权不允许自托管到网站上。** Apple 官网能用 `@font-face` 托管 SF Pro 的 woff2，是因为字体归他们所有；第三方站点这么做是违规的。

但 SF Pro 在苹果设备上是**系统字体**，通过 `-apple-system` 调用完全合法。这也正是 `apple-design` skill 的建议：

> "Default to the platform's system font before a custom face; it already ships optical sizing, tracking tables, and legibility tuning."

### 字体栈

```css
--font-sans:
  -apple-system, BlinkMacSystemFont, "SF Pro Text", "SF Pro Display",
  "Helvetica Neue", Inter, "PingFang SC", "Noto Sans SC",
  "Segoe UI", "Microsoft YaHei", sans-serif;
```

按字符逐个回落，所以两个平台各得其所：

| 平台 | 拉丁文 | 中文 |
|---|---|---|
| **苹果设备** | **SF Pro**（`-apple-system`） | **PingFang SC** |
| Windows / Android | Inter（Web 字体） | Noto Sans SC（Web 字体） |

**PingFang SC 是关键收益**——它是苹果专门为搭配 SF Pro 设计的中文字体，比之前的 Noto Sans SC 协调得多。这个站主要是中文，所以实际观感提升主要来自这里。

另加 `font-optical-sizing: auto`，光学尺寸交给系统。

**实测验证**（本机是 macOS，能看到真实解析结果）：

```
h1               → PingFang SC
.eyebrow         → .SF NS        ← macOS 里 SF Pro 的内部名
.hero-rail strong→ .SF NS
input            → PingFang SC
```

> Web 字体不会被浪费：浏览器只在实际用到某个字族时才下载它。苹果设备上 Inter / Noto Sans SC 不参与渲染，也就不会被下载。

### 换字体后必须重验光学居中

字体度量变了，之前调好的光学补偿会失效。实测：

| 控件 | 换字体后 | 处理 |
|---|---|---|
| 登录按钮 | 0.00px | 原来的 1px 补偿对 PingFang 依然成立，不动 |
| 技能标签 | −0.05px | 在容差内，不动 |
| **主按钮** | **−0.98px** | 需要补偿 |

修主按钮时我先过校正了一次：把 `padding` 上下各改 1px，以为位移 0.5px，实际是 **1px**（差值从 −0.98 变成 +1.02）。

原因很简单——`align-items: center` 下，上内边距 +1、下内边距 −1，内容区的中心就移动了整整 1px，不是 0.5px。改成 `12.5px / 11.5px`（半像素，且总高不变）后归零。

最终三个控件全部 ≤ 0.05px。

> **教训**：改字体家族后，所有手工调过的光学偏移都要重新量一遍。这类补偿是绑死在具体字体度量上的。

## 二十、导航改回通栏（修正浮岛）+ 细节审计

### 浮岛是个误判

上一版把导航做成了**居中悬浮胶囊岛**。那其实是 **iOS 26 浮动标签栏**的模式，**不是 apple.com 的做法**。

抓取印证了 Apple 的结构：**通栏、品牌最左、功能入口最右、导航栏里没有任何实心背景按钮**。（CSS 数值仍抓不到，页面是 JS 渲染的，尺寸按已知特征实现。）

「把导航居中」在 Apple 的语汇里是**内容居中在定宽容器里**，而不是把整个条缩成一颗药丸。

### 现在的做法

```css
.site-header {
  width: 100%; height: 44px;
  /* 用内边距把内容框在 1024px 并居中 —— 通栏 + 内容居中 */
  padding: 0 max(22px, calc((100vw - 1024px) / 2));
  justify-content: space-between;
  background: rgba(251, 251, 253, 0.82);   /* Apple 的近白，不是纯白 */
  backdrop-filter: saturate(180%) blur(20px);
}
.site-header .nav-links { flex: 1; justify-content: space-evenly; }
```

实测：通栏 1440px，内容精确框在 **1024px 居中**，项目间距 102/103 交替，**标准差 0.5px**。

**登录改成绿色文字链**，不再是实心胶囊——这是导航条里没有实心按钮那条的直接结果。之前那颗胶囊「重心不对」的根因也就此消失了。

### 细节审计（写了脚本逐项量）

| 项 | 发现 | 处理 |
|---|---|---|
| 键盘焦点环 | 全部有 | — |
| 光学居中 | 9 个技能小标签偏 1.11px | 补 0.5px 半像素 |
| | 另有几处偏 1.00px | **纯文字链（内边距 0），不适用**——文字在自己的行盒里，没有「居中」可言 |
| 锚点跳转 | `scroll-margin-top: 88px` 但导航只有 44px | 改 60px |
| 焦点环时机 | 鼠标点击也冒框 | 改 `:focus-visible`，只在键盘导航时出现 |
| 禁用态 | **完全没有样式** | 加 `opacity .4` + `not-allowed`；分组进行中按钮现在看得出在忙 |
| 数字输入 | 非等宽，输入时字宽会跳 | `tabular-nums` |
| 移动端点击高亮 | 默认灰方块，和圆角控件对不上 | 改透明 |

验证结果：光学居中真盒子**全部达标**；鼠标点击 `outline: none`、键盘 Tab `solid 2px`；禁用态 `opacity 0.45` + `not-allowed`。

### 两个测试上的坑（都咬过我）

1. **读取带过渡的属性要等过渡跑完。** 设 `disabled` 后立刻读 `opacity` 得到 1，因为 `.button` 有 `opacity 140ms` 过渡。加 400ms 延时才是真实值。
2. **纯文字链不适用「光学居中」检查。** 它的盒子就是行盒，ink 相对盒子的偏移只是字体 ascent/descent 的固有不对称，不是缺陷。审计脚本要按「上下内边距 ≥ 2px」过滤，否则全是假阳性。

## 二十一、Liquid Glass 重做

### 之前做的是「磨砂」不是「液态玻璃」

原实现：`rgba(255,255,255,.5)` + `blur(28px)` + `brightness(1.04)`。这是 iOS 7–15 那种 frosted 材质——把背后糊没了，看起来像一块盖上去的塑料板。

真 Liquid Glass 的差别在三处：

1. **更透、更少模糊** —— 背后的内容要能看见形状
2. **自适应提亮** —— 把背后内容整体抬亮，保留形状与色相，让暗部不吃掉文字
3. **边缘折射** —— 亮镜面线紧挨一条暗折射线

### 用对比实验定参数，不靠猜

做了三轮离屏对比（把不同参数的条压在同一张照片上截图比较）：

**第一轮**：现状磨砂 / 更透 / 加边缘折射 → 发现真正的失败点是**深色照片上文字读不清**。

**第二轮**：提亮 1.5 / 1.7 / 1.85 / 2.0 → 1.85 文字最稳，但背后被洗白，还是「灰板」。

**第三轮（关键）**：降提亮 + 给文字加白色微光 → **1.35 + 微光** 胜出。球衣、墙色都能透过玻璃看见，文字依然清晰。

**定稿**：

```css
background: rgba(255, 255, 255, 0.20);
backdrop-filter: blur(16px) saturate(200%) brightness(1.35) contrast(0.95);
box-shadow:
  inset 0 1px 0 rgba(255,255,255,.9),        /* 顶部镜面高光 */
  inset 0 2px 3px -2px rgba(0,0,0,.16),      /* 紧挨的暗折射线 */
  inset 0 -1px 0 rgba(255,255,255,.38);
/* vibrancy：白色微光把文字从杂乱背景上托起来 */
text-shadow: 0 0 8px rgba(255,255,255,.85), 0 0 2px rgba(255,255,255,.9);
```

关键认知：**不靠压暗/洗白背景来保证可读性，靠给文字做 vibrancy。** 这正是 skill 里那句「别用平灰，提对比、加字重」的实际含义——保住玻璃的透感，代价由文字那边承担。

### 一个必须说的现实：这个站上玻璃没什么可折射的

用像素采样验证材质是否真的在工作（对比导航条内 vs 条正下方同一列的像素）：

```
x= 200  条内=rgb(245,245,247)  条下=rgb(12,12,17)
x= 700  条内=rgb(245,245,247)  条下=rgb(201,25,55)   ← 红墙
x= 400  条内=rgb(79,79,80)     条下=rgb(226,207,208)
```

材质确实在采样（条内条下完全不同）。但**条后面大多是 `rgb(245,245,247)`，也就是 `#f5f5f7` 区块底色**，不是照片。

原因：各区块顶部有 88px 白色内边距，照片基本不会经过导航条后面。玻璃再好，没内容可折射也看不出来。

**要让玻璃真正发挥，最自然的做法是给首屏加一张满幅大图**——让导航条压在照片上。这也正是 Apple 官网的做法（导航常年压在 hero 大图上），而且这个站是摄影社、`assets/` 里还有 63 张没用的照片。

这一步我没做，因为超出了「把玻璃调对」的范围。但如果觉得玻璃still不够味，**问题多半不在参数，而在它背后没东西**。

## 二十二、真·Liquid Glass：折射（feDisplacementMap）

### 之前一直做错在哪

前几版都是「模糊 + 提亮 + 渐变高光」。那是**磨砂**，不是液态玻璃。查了资料才明白关键：

> **真正的 Liquid Glass 核心是折射（refraction），不是模糊。**

光穿过玻璃棱边会弯折，所以背后的画面在边缘处会被**位移、压缩**。纯 `blur()` 永远做不出这个。

### 正确做法

用 SVG 的 `feDisplacementMap`，通过 `backdrop-filter: url(#滤镜)` 作用在背景上：

```xml
<filter id="liquid-glass" color-interpolation-filters="sRGB">
  <feImage id="glass-map" result="map" preserveAspectRatio="none" />
  <feDisplacementMap in="SourceGraphic" in2="map"
                     scale="15" xChannelSelector="R" yChannelSelector="G" />
  <feGaussianBlur stdDeviation="2.2" />
  <feComponentTransfer>…轻微提亮…</feComponentTransfer>
</filter>
```

**位移贴图**（`script.js` 的 `setupLiquidGlass`）按浮岛实际尺寸生成：

- R 通道 = 横向位移，G 通道 = 纵向位移，**128 表示不位移**
- 方向取圆角矩形**有向距离场（SDF）的梯度**，也就是棱边的外法线
- 强度只在距边缘 `bezel` 像素内非零 —— 中间是平的，**光只在边上弯**
- 衰减用二次曲线 `t²`，像真实透镜而不是线性斜坡

尺寸没变就不重建（重建很贵），resize 时防抖 180ms 重算。

### 怎么验证折射真的生效

**在浮岛后面放规则条纹**——有折射的话，条纹在圆角处会被压缩弯折。实测：左右圆角处条纹明显弯折、中间保持平直。这是纯模糊做不出来的，可以当作以后的回归判据。

### 两个限制（必须知道）

1. **只有 Chromium 支持** `backdrop-filter` 引用 SVG 滤镜——这不在 CSS 规范里。Safari / Firefox 会回落到「模糊 + 提亮」版本，**版式完全一致，只是没有弯折**。用 `@supports (backdrop-filter: url(#liquid-glass))` 分流。
   > 社员多数用 iPhone，Safari 上看到的是回落版。所以回落版本身也必须好看。
2. **只对固定尺寸的圆角矩形/圆形可靠**——贴图尺寸要和元素尺寸对齐。这也是为什么导航是圆角矩形浮岛而不是通栏条。

### 参数

浮岛 480×54、圆角 22px、bezel 18px、位移 scale 15px、底色白 14%。
导航文字对比度实测最低 **8.04:1**。

- [w3c/svgwg#1142 — 为「liquid glass」定义可互操作的背景折射](https://github.com/w3c/svgwg/issues/1142)

## 二十三、对照 liquid-glass-design skill 的复查

`affaan-M/ECC/docs/zh-CN/skills/liquid-glass-design` 这个 skill 是**纯原生的**——SwiftUI `.glassEffect()`、UIKit `UIGlassEffect`、WidgetKit，**没有任何 CSS/Web 实现**，不能直接照搬。但它的原则和反模式清单可以拿来对照。

### 逐条对照结果

| skill 的反模式 | 本站情况 |
|---|---|
| 多个独立玻璃不用 `GlassEffectContainer` 包 | ✅ 品牌/链接/登录在**同一块**玻璃里，等价于 Container |
| 玻璃层层嵌套 | ✅ 有脚本验证「无相叠」 |
| **玻璃背后是不透明背景（毁掉通透性）** | ⚠️ **这正是前几轮卡住的原因**——白色区块挡在后面，后来靠首屏大图解决 |
| 忘记裁剪圆角 | ✅ |
| 给所有东西都上玻璃 | ✅ 只有工具条、浮动按钮、弹层、提示 |
| 文字对比度不达标 | ✅ 实测最低 8.04:1 |

### 抓到一个真 bug：无障碍偏好被 `!important` 盖掉了

`prefers-reduced-transparency: reduce` 的规则在 **3224 行**，而折射玻璃规则在 **3740 行**——**两条都带 `!important`，靠后的赢**。等于用户开了「减少透明度」，折射玻璃照样生效，偏好被无视。

修法：把无障碍覆盖挪到文件**最末尾**（3796 行）。

> **教训**：`!important` 之间比的是文件顺序。无障碍类的覆盖规则必须放在最后，否则后续任何带 `!important` 的样式都会把它顶掉。这种 bug 不会报错、日常也看不见，只有开了偏好的用户会中招。

### 补上 skill 里唯一缺的 `.interactive()`

skill 说可交互的玻璃要响应指针，且**明确只给可交互元素**（「不要给所有东西都上玻璃」）。所以：

- `#back-to-top`（玻璃按钮）→ hover 放大 1.06 + 加深落影，press 缩到 0.96
- 浮岛内的链接/登录 → hover 局部提亮，press 缩到 0.97
- **演示角标不加** —— 它是被动标签，不是可交互元素

全部在 `prefers-reduced-motion` 下取消位移。
